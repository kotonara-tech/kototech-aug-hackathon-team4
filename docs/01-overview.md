## 1. 目的

スマートフォンをエッジデバイスとした**定点観測システム**を作る。

- Android 端末が数分ごとに写真を撮影し、Google Drive の AppData 領域へアップロードする
- Web アプリケーションが同じ領域をポーリングし、撮影された写真を観測する

**今回のゴールはローカルでの動作**です。本番運用・公開審査・スケールは対象外。

---

## 2. 動作契約: 1 Google アカウント = 1 端末 = 1 Web クライアント

端末とのペアリングという概念は存在しますが、**今回は実装しません。**

> AppData 領域に書き込む端末が 1 台しかいない。
> だから、読み出す側も 1 台に限定してよい。

この制約を受け入れることで、以下がすべて不要になります。

- 端末 ID の発行・登録・照合
- 複数端末のデータ分離（フォルダ分け、メタデータ、命名規則の拡張）
- ペアリング状態の永続化と、その同期
- サーバーサイドの認可ロジック（そもそもサーバーがない）

**この単純化が設計の中核です。** 実装コストを下げるために意図的に選んだ制約であって、
手抜きではありません。

### 契約が破れたときに何が起きるか

同じアカウントで 2 台目にインストールすると、両方が同じ領域に同じ命名規則で書き込み、
**Web からは 2 台の画像が混ざって見えます。区別する手段はありません。**

これを**検知も防御もしません**（→ [Q14](00-openquestion.md#-q14-1-端末契約が破れるケース)）。
運用契約として守るものです。

### 「複数端末に対応したい」と言われたら

それはこのシステムの**再設計**であって、拡張ではありません。
端末識別・データ分離・認可のすべてが戻ってきます。安請け合いしないでください。

## 3. アーキテクチャ

```
┌──────────────────────────┐              ┌──────────────────────────┐
│   Android (Kotlin)       │              │   Web (React + Vite)     │
│                          │              │   SPA / 静的・サーバーなし │
│   Foreground Service     │              │                          │
│    └ N 分ごとに撮影       │              │   setInterval でポーリング │
│      CameraX             │              │                          │
│                          │              │                          │
│   scope: drive.appdata   │              │   scope: drive.appdata    │
└────────────┬─────────────┘              └────────────▲─────────────┘
             │                                         │
             │ files.create                            │ files.list
             │ (multipart upload)                      │ files.get?alt=media
             │                                         │
             ▼                                         │
   ┌──────────────────────────────────────────────────────────────┐
   │        Google Drive — appDataFolder（隠し領域）                │
   │                                                              │
   │            CAM001_20260822_063000.jpg                        │
   │            CAM001_20260822_063500.jpg                        │
   │            CAM001_20260822_064000.jpg                        │
   └──────────────────────────────────────────────────────────────┘
              ※ drive.google.com からは見えない
              ※ 同一 GCP プロジェクトのクライアントだけが到達できる
```

### サーバーは存在しない

Native も Web も、**ユーザー本人の OAuth アクセストークンで Google Drive API を直接叩きます。**

- バックエンド API サーバーなし
- BFF なし
- データベースなし
- サーバーサイドの秘密（クライアントシークレット、サービスアカウント鍵）なし

**Drive の AppData 領域が唯一の永続層です。**
DB を導入したくなったら、それはこのシステムの再設計です。

### データフロー

1. Android がフォアグラウンドサービス内で N 分ごとに撮影し、端末内に一時保存する
2. 撮影直後に `appDataFolder` へ multipart アップロードする
3. Web SPA が M 秒ごとに `spaces=appDataFolder` でファイル一覧を取得する
4. 一覧に差分があれば、新しい画像の実体を取得して表示する

**両者は Drive を介してのみ結合します。** 互いの存在を知りません。
Android は「誰かが読むかもしれない場所に置く」だけ、Web は「誰かが置いた場所を読む」だけです。

## 4. 責務分担

| | Native (Android) | Web (SPA) |
|---|---|---|
| **役割** | 撮って、送る | 読んで、見せる |
| **Drive 操作** | 書き込みのみ（`files.create`） | 読み出しのみ（`files.list`, `files.get`） |
| **状態** | 撮影セッションの状態のみ（端末内） | ポーリング結果のみ（メモリ） |
| **やらないこと** | 一覧取得・ギャラリー表示・Web との同期 | 書き込み・削除・端末の制御 |

**Native は Drive 上のファイル一覧を取得しません。** 自分が何を上げたかも覚えません。
「撮って、送って、忘れる」だけです。

**Web は Drive に書き込みません。** 読み取り専用のクライアントとして振る舞います
（スコープ上は `drive.appdata` で書き込めますが、実装しません）。

## 5. 設計原則

### 5.1 ポーリングのみ。SSE / WebSocket は使わない

Web 側は Google Drive を**ポーリングするだけ**です。リアルタイム通信機構は導入しません。

**理由**: サーバーがない以上、プッシュの受け口が作れません。Drive の変更通知
（`changes.watch`）は受信用の公開 HTTPS エンドポイントを要求するため、SPA 単体では
成立しません。

**リアルタイム性が必要なら、ポーリング間隔を短くして殴ります。**
力技であることは承知の上での選択です。間隔は UI から可変にしておきます
（→ [Q4](00-openquestion.md#-q4-ポーリング間隔の既定値と可変範囲)）。

### 5.2 Native はアップロードに専念する

「撮って、送る」以外はやりません。責務を増やすと、そのぶん端末上で壊れます。

### 5.3 撮影間隔はハードコードする

設定 UI は作りません。定数 1 つで持ちます。変更したければ再ビルドします。
1 端末・ローカル動作前提なので、これで足ります。
（値は未決 → [Q3](00-openquestion.md#-q3-撮影間隔の具体値)）

### 5.4 トークンは更新しない

SPA ではクライアントシークレットを使えないため、リフレッシュトークンは取得できません。
アクセストークンは約 1 時間で失効します。

**401 / 403 を受けたら、再ログインを促して終わりです。**
黙って再試行するループを作らないでください。失効したトークンで叩き続けても復活しません。

### 5.5 自動再送キューを作らない

Native の送信が失敗したら、ファイルを端末に残してエラーを表示するだけです。
再送は次の撮影サイクルでも試みません。手動で停止 → 開始を許容します。

**理由**: キューを持つと、永続化・順序保証・重複排除・失敗の打ち切りがすべて要ります。
1 端末・ローカル動作のゴールに対して割に合いません。

### 5.6 テストは外部 API を叩かない

Drive API はフェイク実装（Kotlin: MockWebServer / TypeScript: フェイク関数）に
差し替えてテストします。**ネットワークに依存するテストは、当日必ず落ちます。**

### 5.7 TDD で進める

Red → Green → Refactor。**テストを書かずに本体コードを追加しないでください。**
テスト名は日本語で「何を保証するか」を書きます。

## 6. 技術スタック

| | 採用 | 理由 |
|---|---|---|
| Native | **Kotlin** + CameraX + Foreground Service | 数分間隔の定期撮影には常駐サービスが必須。`WorkManager` は最小間隔 15 分で要件を満たせない。Flutter だと結局 Kotlin プラグインを書くことになる |
| Web | **React + Vite + TypeScript** | サーバーを持たない静的 SPA。ホスティングが容易 |
| 永続層 | **Google Drive AppData 領域** | ユーザーのマイドライブを汚さず、誤削除されない。1 アカウント契約と相性が良い |
| 認証 | ユーザー本人の OAuth | サーバーが鍵を持たない。他人のデータは原理的に見えない |

### 破棄した旧実装

| 旧 | 新 | 備考 |
|---|---|---|
| `legacy/native-app/` Flutter 3.47 | Kotlin へ全面書き直し（`native/android/`） | 移植できるのはファイル名規約と撮影セッションの状態遷移の考え方のみ |
| `legacy/web-app/` FastAPI + Jinja2 | React SPA へ全面書き直し | サーバーを持たない方針のため |
| マイドライブ `FarmCameraPOC` フォルダ | `appDataFolder` | スコープも `drive.file`/`drive.readonly` → `drive.appdata` |

旧実装は `legacy/` へ退避済み（→ [Q2](00-openquestion.md) は Close）。

## 7. 非機能要件と、その割り切り

| 項目 | 方針 |
|---|---|
| **可用性** | 保証しない。端末が落ちたら止まる。復帰機構は入れない（→ [Q10](00-openquestion.md)） |
| **データ欠損** | 許容する。送信失敗分は端末に残るが自動再送しない |
| **長期運用** | **不可。** 削除機構がないため画像が無限に増え、ユーザーの Drive 容量を食い潰す（→ [Q5](00-openquestion.md)） |
| **同時接続** | 1 クライアントのみ。複数タブで開いた場合の動作は未定義 |
| **セキュリティ** | サーバーに秘密がない。トークンはブラウザのメモリ上のみ（→ [Q7](00-openquestion.md)）。HTTPS 前提 |
| **スケール** | 対象外。1 アカウント 1 端末が上限 |
| **公開** | 対象外。OAuth はテストモードのまま運用する |

## 8. 実装の着手順序

依存関係があります。**この順で進めてください。**

```
[現実] GCP プロジェクト作成・Drive API 有効化・同意画面・クライアント ID 発行
   │
   ▼
[検証] ★ AppData が両クライアントから共有されることの実地確認  ← 最優先
   │     （02-google-drive.md 7 節。失敗したら設計をやり直す）
   │
   ├──────────────────────┬──────────────────────┐
   ▼                      ▼                      │
[Native] 撮影 → 送信      [Web] ログイン → 一覧    │
   │                      │                      │
   └──────────┬───────────┘                      │
              ▼                                  │
        [つなぎ込み] 実データでの結合確認  ◀───────┘
```

**★ の検証が通るまで、Native と Web の実装に人手を割かないでください。**
ここが崩れると、書いたコードは全部無駄になります
（→ [Q1](00-openquestion.md#-q1-appdata-領域は本当に-android-と-web-で共有されるのか未検証)）。
