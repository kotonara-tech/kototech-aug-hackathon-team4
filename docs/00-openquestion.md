### 状態の定義

| 状態 | 意味 | 実装者の振る舞い |

| `Pending` | 何らかの理由により後回しにされている | 暫定値で進めてよい。**後で必ず戻ってくる**ので、値は 1 箇所に閉じ込める |

## Q4. ポーリング間隔の既定値と可変範囲

**状態: Pending / 影響: 通常**

Web SPA のポーリング間隔は UI から可変にする方針だけが決まっています。

- 既定値は何秒か
- 選択肢は何を並べるか（例: 10 秒 / 30 秒 / 1 分 / 5 分）
- 下限は何秒か。Drive API のレート制限（ユーザーあたり毎分のクエリ数）に当たると
  429 が返ります。1 クライアントしかいないので現実的には余裕がありますが、
  下限なしにすると事故ります

**決めるべきこと**: 既定値・選択肢・下限。

**暫定**: 既定 **30 秒**、選択肢 `[10s, 30s, 1m, 5m]`、下限 10 秒。

## Q5. AppData 領域に溜まり続ける画像を誰が消すのか

**状態: Pending / 影響: 通常**

**現設計に削除機構がありません。** 画像は無限に増えます。

- AppData 領域の使用量は**ユーザーの Drive 容量を消費します**（無料枠 15GB）
- 5 分間隔・1 枚 2MB なら 1 日約 576MB。**約 26 日で 15GB を使い切ります**
- AppData のファイルは drive.google.com から見えないため、
  ユーザーは「容量が減っている理由が分からない」状態になります
- 消す手段は Drive 設定 > アプリの管理（全消し）か、API 経由の `files.delete` のみ

**決めるべきこと**: 誰が、いつ、何を基準に消すのか。候補:

1. **何もしない**（ローカル動作の検証が目的なので、期間中は持つ）
2. Web SPA に手動削除ボタンを付ける
3. Native が古いファイルを自動削除する（N 日より古い、または合計 M 件を超えたら）

**暫定**: 今回はローカル動作がゴールなので **1（何もしない）**。
ただし `01-overview.md` の非機能要件に「長期運用不可」と明記済み。

## Q6. `imageMediaMetadata.time` は appDataFolder でも返るのか

**状態: Open / 影響: 通常**

Web 側は撮影時刻を EXIF (`imageMediaMetadata.time`) 優先で決めます。
Drive がアップロード画像の EXIF を解析してこのフィールドを埋める挙動は、
**AppData 領域でも同様に働くはず**ですが、確認していません。

- 返らない場合、Web は `createdTime`（＝アップロード到着時刻）にフォールバックします
- 圃場は電波が弱く送信が遅れるため、「朝 6 時の写真」が「夕方 18 時」と表示されます
- 代替案: ファイル名 `CAM001_yyyyMMdd_HHmmss.jpg` から撮影時刻をパースする
  （現設計ではファイル名を時刻判定に**使わない**方針。覆す場合はここの決定が必要）

**決めるべきこと**: Q1 の疎通検証と同時に `files.list` のレスポンスを目視し、
`imageMediaMetadata.time` が入っているか確認する。入っていなければ、
ファイル名パースへ方針変更するか判断する。

## Q7. Web のアクセストークンをどこに保持するか

**状態: Pending / 影響: 通常**

SPA なのでリフレッシュトークンは取得できず、アクセストークンは約 1 時間で失効します
（方針決定済み: トークンは更新しない）。

**決めるべきこと**: トークンの保持場所。

- **メモリのみ**（React state）— 最も安全。リロードのたびに再ログイン
- `sessionStorage` — タブを閉じるまで保持。XSS で抜かれる
- `localStorage` — 論外（永続化 + XSS）

**暫定**: **メモリのみ**。デモ中にリロードしなければ困りません。
ポーリング中に失効したら再ログイン画面へ戻します。

## Q8. 一覧の取得上限とページングをどうするか

**状態: Pending / 影響: 通常**

旧 Web 実装は `MAX_PHOTOS=300` で打ち切り、ページ送りなしでした。

- Drive の `files.list` は `pageSize` 最大 1000、`nextPageToken` でページング
- 5 分間隔なら 1 日 288 枚。数日で 300 件を超えます
- 全件読むと初回表示が遅く、画像取得のリクエストも比例して増えます

**決めるべきこと**: 上限値と、超えたときの挙動（打ち切り / ページ送り / 日付絞り込み）。

**暫定**: `pageSize=100` の 1 ページのみ（＝最新 100 件）。
`orderBy=createdTime desc` なので最新側から取れます。

## Q10. 端末の省電力機能でサービスが殺された場合の扱い

**状態: Pending / 影響: 通常**

**決めるべきこと**: 復帰機構を実装するか、運用（該当端末の省電力設定を切る）で回避するか。

**暫定**: **運用で回避**。デモ端末の「バッテリー最適化」を対象外に設定する手順を

## Q12. 署名鍵がビルドマシンに依存する問題

**状態: Pending / 影響: 将来**

Android の OAuth クライアント ID はパッケージ名と署名 SHA-1 の組で登録します。
現在は debug keystore（`%USERPROFILE%\.android\debug.keystore`）を使っており、
**別マシンでビルドすると SHA-1 が変わり、サインインだけが失敗します。**

本番用 GCP プロジェクトでは、同じパッケージ名に対しても**リリース署名鍵の SHA-1**で
Android OAuth クライアントを別途登録します。Google Play App Signing を使う場合は、
Play Console のアプリ署名証明書の SHA-1 を使います。

他は全部動くのにログインだけ通らないため、原因に辿り着きにくい類の障害です。

**決めるべきこと**: ビルド機を 1 台に固定するか、共有の keystore を作ってリポジトリ外で
配布するか。

**暫定**: **ビルド機を固定**。複数人がビルドする必要が出たら再検討。

## Q13. Web SPA のホスティング先

**状態: Pending / 影響: 将来**

「サーバーを持たない = 静的ホスティングが容易」が React + Vite を選んだ理由の一つですが、
**今回のゴールはローカル動作**であり、実際のホスティング先は決めていません。

- ローカルは `http://localhost:5173`（Vite dev server）
- 公開する場合、OAuth クライアントの「承認済みの JavaScript 生成元」に
  そのオリジンを追加登録する作業が発生します
- `drive.appdata` は非機微スコープなので、これだけを使う限りスコープ審査・デモ動画・
  CASA 監査は不要です。公開用 Web OAuth の一般要件（HTTPS、公開ホームページ、
  プライバシーポリシー、利用ドメインの所有確認）は、リリース準備として別途満たします

**決めるべきこと**: 今回はローカルのみで確定してよいか。

## Q14. 「1 端末」契約が破れるケース

**状態: Pending / 影響: 将来**

`CAM001` は固定値で、端末を識別していません。契約が破れるのは:

- アプリを再インストールした場合（同じ `CAM001` で書き続けるので実害なし）
- **同じアカウントで 2 台目にインストールした場合** — 両方が同じ `appDataFolder` に
  同じ命名規則で書き込みます。秒が衝突しない限りファイルは共存しますが、
  **Web からは 2 台の画像が混ざって一覧に出ます。区別する手段がありません**
- 端末を機種変更した場合（旧端末をアンインストールすれば実害なし）

**決めるべきこと**: 破れたことを検知する必要があるか。

**暫定**: **検知しない。** 運用契約として「1 アカウントに 1 端末」を守る。
これはシステムの前提であって、防御する対象ではありません（`01-overview.md` 2 節）。

## Q16. 端末に残す JPEG の扱い

**状態: Open / 影響: 通常**

[03 §6](03-native.md) は「端末の**一時ディレクトリ**へ保存」、
[03 §11](03-native.md) は「**送信失敗時にファイルを削除しないこと**」と定めている。
この2つに次を重ねると、規約が観測可能な効果を持たない。

- 自動再送キューは作らない（[01 §5.5](01-overview.md)）
- Native は一覧取得もギャラリー表示もしない（[01 §4](01-overview.md)）
- 保存先の `cacheDir` は **OS がストレージ逼迫時に予告なく消せる**

つまり**残したファイルを読む主体がどこにも存在せず、しかも OS がいつでも消せる。**

| 案 | 内容 | 備考 |
|---|---|---|
| A | 現状の文面どおり `cacheDir` に置いて放置 | 実装ゼロ。規約は空文のまま |
| B | 送信成功したら消し、失敗ぶんだけ残す | 「残す」が観測可能な事実になる。`adb pull` での手動回収はできる |
| C | アプリ専用の永続領域へ置き、件数上限で古いものから消す | 手動回収やログ突き合わせに使える。実装コストは最大 |

**決めるべきこと**: A / B / C のいずれか。

**暫定**: 議論を継続する。M1 の `CaptureCoordinator` は**保存の責務を差し替えられる形**に
しておき、どの案に決まっても変更が1箇所で済むようにする
（→ [05 §5-3](05-implementation-plan.md)）。

> Q5（`appDataFolder` に溜まる画像を誰が消すのか）とは**別問題**。Q5 は Drive 側、
> Q16 は端末側の話で、Q5 の暫定決着（何もしない）に影響されない。
